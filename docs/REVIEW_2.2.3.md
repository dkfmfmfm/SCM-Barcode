# BeyondPack 2.2.3 기술 검토 — 장점·결함·개선 우선순위

검토 대상: `main` 브랜치 `90f9a13` (BeyondPack 2.2.3)
검토 방식: 전체 소스 정독 + 실제 실행 계측(35개 단위시험 통과 확인, 20만건 상품DB 부하 측정, Excel 내보내기·박스번호·데이터 예외 재현)
검토 기준: `PLAN.MD` 인수기준, `RESEARCH.MD` 글로벌 벤치마크, 대형 물류창고 확장 목표

> **조치 현황.** P0-3(라벨 용지 규격·자동 출력)과 현장에서 발견된 라벨 순번 누락은 [2.2.4](RELEASE_2.2.4.md)에서, P0-1의 **박스번호 중복**은 [2.2.5](RELEASE_2.2.5.md)에서 출고건 단위 발번으로, 용지 지정이 조용히 실패하던 문제는 [2.2.6](RELEASE_2.2.6.md)에서 수정했다. P0-4(실적 소실)는 [2.2.8](RELEASE_2.2.8.md)의 자동 백업으로 완화했다. P0-2(라벨 바코드), P0-5(시트 인증), P2-3(다작업대 발번)은 미해결이다.

`RESEARCH.MD` 4장은 **v1.4(첨부 ZIP)** 를 대상으로 한 전략 분석이다. 이 문서는 그 이후 새로 구현된 **2.2.3 코드 자체**를 대상으로 하며, 문서 수준이 아니라 파일·행 단위의 확인된 사실과 실측값만 기록한다.

## 0. 한 줄 결론

> 2.2.3은 **"단일 포장 작업대용 오프라인 우선 조회 도구"로는 동급 자체제작 도구 상위 수준**이다. 데이터 파이프라인(동기화·검증·원자 교체·장애 격리)은 상용 제품에 견줄 만큼 잘 설계되어 있다.
> 반면 **작업 결과물 쪽(라벨·박스 식별자·실적 보관·이력 관리)은 v1.4보다 오히려 후퇴한 영역이 있고**, 대형 창고로 가기 위한 구조(중앙 원장·다작업대·재고)는 설계상 아직 존재하지 않는다.
> 즉 **"들어오는 데이터는 신뢰할 수 있는데, 나가는 결과물은 아직 신뢰의 단위(unit of record)가 아니다."**

## 1. 현재 아키텍처 요약

```text
Google Sheet(BeyondPack 탭)
  └─ CSV export URL (인증 없음)          sources/google_sheets.py
       └─ rows_to_batch: 헤더·버전·스키마 검증   sources/tabular.py
            └─ map_product: 별칭 매핑·상태 정규화 sources/mapping.py
                 └─ replace_snapshot: 전량 검증 → 새 SQLite 파일 생성 → 무결성검사
                    → manifest(products.current.json) 포인터 전환     cache.py
                         └─ 조회: FNSKU+CountryCode 로컬 인덱스        cache.py:lookup
                              └─ 포장 입력·확정 → packaging.db(로컬)    packaging.py
                                   └─ 라벨(HTML→QPrinter) / Excel 수동 저장
```

| 계층 | 구현 | 평가 |
|---|---|---|
| 상품 동기화 | 백그라운드 QThread, 실패 시 기존 DB 유지 | 우수 |
| 상품 저장 | 불변 스냅샷 + 매니페스트 포인터 + 직전본 보존 | 우수 |
| 조회 | 로컬 SQLite, 복합키(FNSKU+국가) | 정확하나 인덱스 미최적 |
| 포장 기록 | 로컬 SQLite(WAL), 감사 테이블 존재 | 기록은 되나 활용 경로 없음 |
| 산출물 | 텍스트 라벨, 수동 Excel | **가장 약한 고리** |
| 배포 | Inno Setup 설치본 + 포터블 + 단일 EXE + SHA256 | 우수(코드서명만 미비) |

## 3. 강점 (유지해야 할 것)

### 3.1 상품DB 교체가 절대 현장을 멈추지 않는다 — 최고 수준의 설계

`cache.py:61-95`의 `replace_snapshot`은 **검증 → 새 파일 작성 → 무결성 검사 → 매니페스트 포인터 전환** 순서다.
기존 DB를 덮어쓰지 않으므로 백신·백업 에이전트가 파일을 잡고 있어도 업데이트가 실패하지 않는다(`products.snapshot.<PID>.<UUID>.db`, `cache.py:49-50`). 실패하면 새 파일만 지우고 활성 포인터는 그대로다.
Windows 파일 잠금 재시도(`_replace_with_retry`, `cache.py:165-176`)까지 넣은 것은 현장 사고를 실제로 겪어본 설계다. 상용 데스크톱 도구에서도 흔치 않다.

### 3.2 잘못된 마스터가 현장에 도달하지 못한다 — 5중 차단

| 차단 | 위치 |
|---|---|
| 필수 열 누락 | `sources/tabular.py:37-42` |
| DataVersion/SchemaVersion 혼재 | `sources/tabular.py:44-66` |
| 동일 FNSKU+국가 중복 | `cache.py:305-307` |
| 상품 수 20% 이상 급감 | `cache.py:68-72` |
| SQLite 무결성·건수 불일치 | `cache.py:392-397` |

"부분 반영"이 없다. 전량 통과 아니면 전량 거부이므로 반쪽짜리 상품DB가 생길 수 없다. 이것이 이 프로그램의 가장 큰 자산이다.

### 3.3 국가 복합키 결정이 도메인에 정확히 맞는다

동일 FNSKU가 마켓플레이스별로 존재하는 Amazon 현실을 `FNSKU|CountryCode`로 정면 처리했고(`normalization.py:24-29`), 국가가 틀리면 **등록된 국가를 알려주는** 오류를 준다(`cache.py:225-229`). 작업자가 스스로 복구할 수 있는 오류 메시지다.

### 3.4 장애 상태를 숨기지 않는다

`CURRENT / CACHED / SYNCING / ERROR / NO_DATA` 5색 배너(`ui.py:54-60`)와 "다음 행동" 안내(`ui.py:308`)로, 작업자가 **지금 쓰는 데이터가 최신인지 캐시인지** 항상 알 수 있다. 오프라인 우선 도구의 필수 요건을 충족한다.

### 3.5 릴리스 공정이 이미 제품 수준

Windows CI에서 단위시험 → 포터블/단일EXE 빌드 → **실제 GUI 창 생성 self-test** → Inno Setup 설치본 → SHA256 → 릴리스 게시까지 자동화되어 있다(`.github/workflows/release-windows.yml`). GUI self-test를 CI에 넣은 것은 특히 좋다.

### 3.6 오류코드·진단 체계

`BP-CFG/AUTH/SRC/DATA/LOOKUP/PACK-xxx` 체계(`errors.py`)와 진단 ZIP(`diagnostics.py`)은 원격 지원 비용을 실제로 낮춘다. 진단 파일에서 `token` 포함 파일을 제외하는 처리(`diagnostics.py:33`)도 적절하다.

## 4. 결함과 위험

심각도: **P0** = 현장 사고·데이터 소실 직결 / **P1** = 품질·생산성 저해 / **P2** = 확장·유지보수 부채

---

### P0-1. 박스번호가 전역 유일하지 않다 — 라벨이 서로 구분되지 않는다

**현상.** `job_id`는 프로그램 실행 후 **첫 확정 시 1회만** 생성된다(`ui.py:695-700`). 박스 시작번호는 그 job 안에서만 이어진다(`packaging.py:122-127`). 따라서 프로그램을 껐다 켜면 박스번호가 **1부터 다시 시작**한다. 라벨에는 `BOX {번호}`만 인쇄된다(`labels.py:31`).

**실측.**

```text
job1 그룹1 → BOX 1~3
job1 그룹2 → BOX 4~6
job2 그룹1 → BOX 1~3   ← 프로그램 재시작 후 번호 중복
```

**영향.** 같은 날 같은 쉽먼트에 "BOX 1" 라벨이 여러 장 존재한다. 검수·재출력·클레임 대조 시 어느 박스인지 식별 불가. 대형 창고에서는 즉시 사고로 이어진다.

**수정.** 라벨과 DB에 전역 유일 식별자를 부여한다. 최소안은 `작업일자-작업대ID-연번`(예: `20260812-PC03-000147`), 목표안은 `RESEARCH.MD` 8.2의 SSCC/LPN. 라벨에는 사람판독문자와 바코드를 함께 인쇄한다.

---

### P0-2. 라벨에 바코드가 없다 — 물류 라벨이 아니라 인쇄물이다

**현상.** `labels.py` 전체가 텍스트 HTML 표다. 코드베이스 전체에 `barcode / Code128 / DataMatrix / GS1` 관련 구현이 없다(전수 검색 확인).

**영향.** 출고 후 어느 공정에서도 이 박스를 스캔할 수 없다. 박스 대조가 100% 눈과 손이다. 스캔 기반 작업으로 전환할 때 라벨을 전부 다시 붙여야 한다.

**수정.** Code128(또는 GS1-128) 1D + DataMatrix 2D를 함께 인쇄. 내용은 박스 전역 ID, 필요 시 쉽먼트 ID·수량. 순수 파이썬 구현(예: 자체 Code128 인코더 + Qt 도형 렌더링)으로 외부 의존성 없이 추가 가능하다.

---

### P0-3. 라벨 용지 규격이 지정되지 않는다 — v1.4 대비 명백한 회귀

**현상.** `ui.py:743-753`은 `QPrinter(HighResolution)` + `QPrintDialog`만 쓰고 **페이지 크기를 지정하지 않는다**(`QPageSize`/`setPageSize` 미사용, 전수 검색 확인). 즉 드라이버 기본값(대개 A4)으로 나간다.

**대비.** `RESEARCH.MD` 4.1/4.3에 따르면 v1.4는 **프린터명·라벨 가로/세로·글자크기·출력 ON/OFF 설정과 가상 프린터(PDF/XPS) 회피**를 갖고 있었다. 2.2.3에는 이 기능이 전부 없다.

**부수 문제.**
- 박스 확정 시 **자동 출력이 없다.** 확정(`confirm_box_group`)은 저장만 하고, 작업자가 별도로 F8을 눌러야 한다(`ui.py:736`).
- 재출력할 때마다 **프린터 선택 대화상자**가 뜬다(`ui.py:744-746`). 100박스 작업이면 100번 뜬다.
- 재출력 대상은 **직전 그룹 하나뿐**이다.

**수정.** 설정에 프린터명·라벨 크기(mm)·여백·폰트 크기 추가, 확정 시 지정 프린터로 무대화상자 출력, 가상 프린터 감지, 실패 시 재시도 큐. 이건 v1.4 기능 복원 수준이며 현장 도입 전 필수다.

---

### P0-4. 포장 실적이 작업 PC에만 존재한다

**현상.** `packaging.db`는 `%LOCALAPPDATA%\BeyondPack\data\`에만 있다(`app.py:140`). 중앙 업로드·자동 백업 경로가 코드에 없다. 유일한 반출은 **현재 작업 하나**를 수동으로 Excel 저장하는 것뿐이다(`ui.py:756-769`, `job_id`가 없으면 아예 불가).

**영향.**
- PC 고장·재설치·랜섬웨어 = 실적 소실. `PLAN.MD`는 제거·업데이트 시 데이터 보존을 보장하지만 **디스크 자체의 소실은 보장하지 않는다.**
- 작업대가 3대면 실적이 3조각으로 흩어지고 통합 집계가 수작업이 된다.
- 어제 작업분을 다시 뽑으려면 `job_id`를 알 수 없어 사실상 불가(§P1-3 참조).

**수정.** 최소안: 종료 시/시간 단위로 일자별 Excel·CSV를 공유 폴더나 Google Sheet에 자동 append. 목표안: 포장실적 수집 API(중앙 DB) + 오프라인 큐 재전송.

---

### P0-5. 상품 마스터가 인증 없이 공개되어야 동작한다

**현상.** `google_sheets.py:38-41`은 `.../export?format=csv&gid=...`를 인증 없이 호출한다. 이 URL이 동작하려면 시트가 **"링크가 있는 모든 사용자" 공개** 상태여야 한다. OAuth·서비스 계정·API 키 경로가 코드에 없다. 응답 서명·해시 검증도 없다(`DataVersion`은 무결성이 아니라 버전 식별용).

**영향.** 링크가 유출되면 전 품목·SKU·FNSKU·Amazon 계정 정보가 외부에 노출된다. `RESEARCH.MD` 4.4-B에서 v1.4의 문제로 지적한 항목이 2.2.3에도 그대로 남아 있다.

**수정.** 서비스 계정(Sheets API) 인증 도입, 또는 관리자가 서명된 스냅샷(`.db` + 서명)을 배포하고 작업대는 서명 검증 후 반영. 최소한 시트 공개범위를 조직 도메인으로 제한하고 URL을 정기 교체.

### P1-1. 조회가 인덱스를 못 쓴다 — 상품 수에 비례해 느려진다 (실측)

**원인.** `cache.py:354-356`은 `normalized_fnsku` 단일 인덱스와 `country_code` 단일 인덱스를 따로 만든다. 조회는 두 열을 AND로 쓰는데(`cache.py:212`), 통계(ANALYZE)가 없어 SQLite가 **선택도가 나쁜 `idx_products_country`를 고른다.**

```text
EXPLAIN QUERY PLAN → SEARCH products USING INDEX idx_products_country (country_code=?)
```

**실측(동일 장비, 중위값).**

| 상품 수 / 국가 수 | 현재 | ANALYZE 후 | 복합인덱스 후 |
|---|---:|---:|---:|
| 2만 / 4개국 | 2.22 ms | 0.335 ms | 0.372 ms |
| 20만 / 4개국 | 23.33 ms | 0.332 ms | 0.334 ms |
| 20만 / 2개국 | 38.59 ms | 0.300 ms | 0.305 ms |

국가당 행 수에 **선형 비례**한다. 지금 규모에서는 체감되지 않지만, 품목이 늘수록 스캔이 눈에 띄게 무거워지고 이는 사용자에게 "프로그램이 느려졌다"로 인식된다.

**수정(1줄 수준).** `CREATE INDEX idx_products_lookup ON products(normalized_fnsku, country_code)` 추가, 스냅샷 작성 직후 `ANALYZE` 실행. **70~130배 개선.**
참고로 `lookup_key`는 열 제약 UNIQUE(`cache.py:352`)와 `idx_products_lookup_key`(`:356`)로 **인덱스가 이중 생성**되어 있다. 하나는 제거해도 된다.

---

### P1-2. Excel 실적의 숫자가 숫자가 아니다 (실측)

**현상.** 무게·치수를 `str(Decimal)`로 TEXT 저장하고(`packaging.py:135-139`), 내보내기는 그 값을 그대로 쓴다(`exporter.py:74`).

```text
무게(kg/BOX)  = '12.345'                    type=str   ← 텍스트
가로(cm)      = '40'                        type=str   ← 텍스트
작업일시      = '2026-08-12T00:10:10+00:00' type=str   ← UTC 문자열
```

**영향.** 총중량 SUM, 피벗, 조건서식, 정렬이 전부 안 된다. 실적 파일을 받는 관리자가 매번 수동 변환한다. 작업일시는 **UTC**라 KST와 9시간 차이 나고 Excel 날짜형도 아니다 — 야간 작업분이 전날로 보인다.

**수정.** 내보내기에서 `Decimal → float`, `created_at → 로컬 시간 datetime` 셀로 변환하고 표시형식을 지정한다. DB의 TEXT 저장(정밀도 보존 목적)은 유지해도 된다.

---

### P1-3. 저장된 작업을 다시 볼 수도, 취소할 수도 없다

**현상.** UI에 작업 이력 화면이 없다. 재출력은 `last_group` 하나(`ui.py:736-753`), Excel 저장은 `self.job_id`(이번 실행분)만(`ui.py:757`). `close_job`은 구현되어 있으나 **어디서도 호출되지 않아** 모든 작업이 영구히 `OPEN`으로 남는다(실측 확인). 확정된 박스그룹을 수정·삭제하는 기능은 없다.

**영향.** 현장에서 오입력은 반드시 발생하는데, 잘못 확정한 박스를 **되돌릴 방법이 프로그램 안에 없다.** DB를 직접 열어 수정하는 것 외에 방법이 없고, 그 순간 감사 추적은 무의미해진다. 어제/지난주 작업 재출력·재수출도 불가.

**수정.** 작업 목록 화면(일자·작업자·박스수 검색) + 박스그룹 선택 재출력 + **사유 필수 취소(void)**. `audit_events.reason` 열은 이미 준비되어 있는데 쓰이지 않는다(`packaging.py:90`).

### P1-4. 감사 로그를 쌓기만 하고 볼 수 없다

`audit_events`에 JOB/BOX_GROUP 생성이 기록되지만(`packaging.py:237-262`) 조회 API·화면·내보내기가 없다. 진단 ZIP에도 포함되지 않는다(`diagnostics.py:50-54`는 `summary.json`과 `sync-status.json`만 담는다). 감사 기능이 사실상 작동하지 않는 상태다.

### P1-5. 작업 리듬이 스캐너에서 끊긴다

| 지점 | 현상 | 근거 |
|---|---|---|
| 수량 입력 후 | Enter로 "추가"가 안 된다. 기본 버튼 미지정, 수량칸에 Enter 핸들러 없음 → **마우스 클릭 필요** | `ui.py:231-242`(전수 검색: `setDefault`·수량칸 `returnPressed` 없음) |
| 확정 | Ctrl+Enter — 한 손으로 어렵다 | `ui.py:381` |
| 스캐너 접미문자 | `scanner_terminator` 설정이 **정의만 되고 어디서도 안 쓰인다** | `config.py:36` (전수 검색 결과 참조 0건) |
| 한글 IME | 입력기 힌트 미설정 → **IME가 한글이면 FNSKU가 깨져 들어간다** | 전수 검색: `setInputMethodHints` 없음 |

특히 **IME 문제는 한국 현장에서 반드시 발생하는 고전적 사고**다. 작업자는 원인을 모른 채 "스캐너가 고장났다"고 보고한다.

**수정.** FNSKU 입력칸에 `Qt.ImhLatinOnly | Qt.ImhNoPredictiveText` 지정 + 포커스 진입 시 IME 해제, 수량칸 Enter = 추가, 확정은 단일키(F12 등) 병행, `scanner_terminator` 실제 구현 또는 제거.

### P1-6. 성공과 오류의 소리가 같다

`_success`와 `_error` 모두 `QApplication.beep()`를 호출한다(`ui.py:833`, `ui.py:840`). 소음이 큰 창고에서 화면을 보지 않고 작업할 때 **성공인지 실패인지 구분할 수 없다.** 색·문구는 잘 구분되어 있으므로 소리만 분리하면 된다(오류는 저음 2연타 등).

---

### P1-7. 박스 규격을 매번 0부터 다시 입력한다

확정·초기화 시 무게·가로·세로·높이가 모두 0으로 리셋되고(`ui.py:713`, `ui.py:729`) `positive_decimal`은 0을 거부하므로(`normalization.py:50-51`) **박스마다 4개 값을 전부 재입력**해야 한다. 표준 박스가 반복되는 현장에서는 순수 낭비이자 오타 원인이다.

또한 **박스그룹당 무게가 1개**다(`models.py:75`). "동일 구성 3박스"라도 실제 중량은 박스마다 다른데 기록할 수 없다. 운송사에 제출하는 실중량과 어긋난다.

**수정.** 박스 규격 프리셋(S/M/L 등록, 선택 시 치수 자동 입력) + 최근값 기억. 중장기적으로 박스별 실중량 입력(저울 연동 시 자동).

---

### P1-8. 저울·치수측정기 연동이 없다

무게와 치수가 100% 수기 입력이다. 잘못 입력해도 검증할 방법이 없고(범위 검사만 존재: `weight_max_kg=1000`, `dimension_max_cm=500`), 그 값이 그대로 운송비 산정 근거가 된다. RS-232/USB 저울 연동은 난이도 대비 효과가 매우 큰 개선이다.

### P1-9. 데이터 예외에서 원인을 오해하게 만드는 메시지 (실측)

| 상황 | 실제 동작 | 문제 |
|---|---|---|
| `Status` 열은 있는데 **값이 빔** | 해당 상품이 조용히 비활성 처리 → 스캔 시 **"사용중지된 상품입니다"**, 국가 목록에서도 사라짐 | 관리자는 시트에 상품이 있는데 왜 안 되는지 알 수 없다. `mapping.py:33-34`가 빈 값을 Published로 보지 않는다 |
| 전 행의 `Status`가 빔 | 업데이트 전체 거부 "게시 상태의 상품이 0건입니다" | 원인이 Status 열이라는 안내가 없다 |
| `CountryCode` 누락 행 2개 이상 | **"동일 FNSKU+국가가 2건 이상 있습니다: "** (빈 키끼리 중복 판정) | 완전히 다른 원인을 지목한다. `cache.py:279-307` |

**수정.** 빈 Status는 Published로 간주하거나 명시적 경고, 키 생성 불가 행은 "국가코드 누락 N행"으로 별도 보고.

### P1-10. 원본 FNSKU 표기가 보존되지 않는다

`cache.py:365`가 `fnsku` 열에도 **정규화값**을 넣는다(원본 컬럼이 사실상 없음). 실측: 마스터의 `x0a-1`이 화면·라벨·Excel에 `X0A-1`로 표시된다. 조회 정확성에는 문제없지만 마스터와 1:1 대조할 때 혼선이 생긴다. 원본 표기를 별도 열로 보존하는 편이 안전하다.

### P2-1. 가장 위험한 파일이 가장 시험되지 않는다

`ui.py` 870행에 화면 구성·업무 규칙·인쇄·초안 저장·오류 처리가 모두 들어 있다. 단위시험 35개는 **전부 비UI 계층**이며(`tests/`), CI의 self-test는 창 생성과 증감 버튼 클릭만 검증한다(`app.py:96-123`). 국가 잠금, 중복 스캔 합산, 초안 복구, 확정 후 초기화 같은 **실제 사고가 나는 로직에 회귀 시험이 없다.**

**수정.** 업무 규칙을 UI에서 분리(예: `PackingSession` 도메인 객체)하고 그 계층에 시험을 붙인다. UI는 표시·입력만 담당.

### P2-2. 관리자 기능이 작업자 화면에 그대로 노출된다

`Sheet 설정`, `Excel 비상 업데이트`, `관리자 진단파일 생성`이 잠금 없이 노출되어 있다(`ui.py:296-304`). 작업자가 임의 Excel로 상품DB를 통째로 바꿀 수 있다. 작업자명도 자유 입력 텍스트(`ui.py:159`)여서 실적 귀속의 신뢰도가 낮다.

**수정.** 관리자 PIN, 작업자 사번 바코드 스캔 로그인.

### P2-3. 다작업대는 구조적으로 불가능하다

동시 실행 방지는 `QLockFile`로 **PC 1대 1인스턴스**까지만이다(`app.py:129-138`). 박스번호 발번, 실적 통합, 중복 작업 방지를 담당하는 중앙 서비스가 없다. 작업대가 2대 이상이 되는 순간 §P0-1이 배로 악화된다.

### P2-4. 그 밖

- **자동 업데이트 없음 + 코드 서명 없음**(README 명시). PC 수가 늘수록 배포·SmartScreen 경고 대응 비용이 선형 증가.
- **한국어 하드코딩**. 해외 창고·외국인 작업자 투입 시 전면 수정 필요.
- **캐시 만료가 경고에 그친다**(`ui.py:402-404`). 며칠 지난 마스터로 계속 작업 가능. 정책상 타당하나 경과일수 강조·관리자 알림이 필요하다.
- **스냅샷 생성 4.28초 / 20만건**(실측, DB 36.8MB). 백그라운드 스레드라 UI는 멈추지 않으며 현 규모에서 문제없다.
- **`available_countries` 131ms / 20만건**(실측). `lower(status)` 때문에 전체 스캔. 호출 빈도가 낮아 당장은 무해하나 status에 인덱스를 쓰려면 저장 시 소문자 정규화가 필요하다.

## 5. 대형 창고 관점의 구조적 공백

아래는 **버그가 아니라 설계 범위 밖**이며, `PLAN.MD` 3.2가 명시적으로 제외한 항목이다. 다만 "향후 큰 물류창고" 목표에서는 반드시 채워야 한다.

| 없는 것 | 없으면 생기는 일 |
|---|---|
| 불변 재고이동 원장 | 어디에 몇 개 있는지 시스템이 답할 수 없다 |
| 입고/출고 구분 | 이 박스가 들어온 것인지 나가는 것인지 데이터에 없다 |
| 로케이션·LPN·팔레트 | 적치·피킹·보충 지시가 불가능 |
| 주문·ASN·Shipment | 무엇을 위한 포장인지 연결되지 않는다 |
| 로트·유통기한·시리얼 | FEFO·리콜 추적 불가 |
| 권한·역할·중앙 감사 | 누가 무엇을 바꿨는지 통제 불가 |
| 모바일(Android 러기드) | 이동 작업·다인 동시 작업 확장 불가 |
| 중앙 프린트 큐 | 라벨 재출력·중복출력 통제 불가 |

`RESEARCH.MD` 9~16장의 목표 프로세스·데이터 모델·로드맵이 그대로 유효하다. **BeyondPack에 이 기능들을 계속 덧붙이는 것은 권장하지 않는다.**

### 다만, 지금 구조에서 가장 가성비 높은 도메인 기능 하나

이미 `FNSKU`, `AmazonAccount`, 국가, 박스별 구성품·수량을 모두 보유하고 있으므로 **Amazon FBA Box Content(박스 내용물 정보) 파일 생성**은 적은 노력으로 큰 효과를 낸다. 현재는 이 정보를 Excel로 뽑아 사람이 다시 FBA에 입력해야 한다. 쉽먼트 ID 필드 하나와 내보내기 포맷만 추가하면 중복 입력과 그로 인한 오류가 사라진다.

## 7. 현장 투입 전 최소 합격선

`PLAN.MD` 17장 인수기준은 충족되어 있으나, 실제 창고 투입 전에 다음이 추가로 필요하다.

- [ ] 실제 라벨 프린터에서 지정 규격으로 출력되고, 확정 시 자동 출력된다
- [ ] 서로 다른 날·다른 PC에서 만든 박스 라벨의 번호가 겹치지 않는다
- [ ] 라벨의 박스 ID를 스캐너로 읽을 수 있다
- [ ] IME가 한글 상태여도 스캔이 정상 동작한다
- [ ] 잘못 확정한 박스를 사유를 남기고 취소할 수 있다
- [ ] 작업 PC가 고장나도 전일 실적이 다른 곳에 남아 있다
- [ ] Excel 실적에서 총중량 SUM이 즉시 계산된다
